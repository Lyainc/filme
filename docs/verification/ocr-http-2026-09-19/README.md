# OCR 실제 HTTP 확인 — 2026-09-19

사용자가 직접 HTTP 200이 나오는지 확인해 달라고 요청해 합성 이미지로 실제 `/api/ocr` POST를 실행했어요. 실제 티켓이 아닌 TEST MOVIE / TEST CINEMA / 2099-01-01 / 12:00 / A1 문구의 512×580 JPEG이며 QR·예매번호·계정 정보는 없어요.

| 환경 | HTTP | 응답 | 소요 시간 |
| --- | --- | --- | --- |
| 기존 로컬 개발 서버 3712 | 500 | HTML 서버 오류 | 4.744초 |
| 배포 filme-web.vercel.app | 500 | Internal Server Error | 6.636초 |
| 별도 로컬 빌드 서버 3714 | 500 | Internal Server Error | 4.339초 |

로컬 개발 서버와 배포 API의 GET은 모두 405와 Method not allowed를 반환했어요. 따라서 POST 처리 경로를 구분해서 조사해야 해요.

별도 로컬 빌드의 로그에서 `FailedToOpenSocket`과 Upstash Redis 주소 연결 실패를 확인했어요. 그 호스트의 DNS 조회도 `ENOTFOUND`로 실패했어요. 호스트 식별자·토큰·원문 로그는 이 문서에 저장하지 않아요. 코드상 `validateOcrRequest`가 먼저 `checkOcrRateLimit`을 기다리고, 그 다음에 인증 및 Gemini 호출로 진행해요. 요청 제한 저장소의 예외가 처리되지 않아 여기서 500으로 끝나며, 로컬에서는 모델 호출 전 실패한 근거가 있어요.

배포 사이트의 500은 실측했지만 배포 함수 로그·환경 변수·연결 대상은 확인하지 않았으므로 동일 Redis 원인으로 확정하지 않아요. DNS 실패가 주소 오타·DB 삭제·일시적 DNS 문제 중 어느 것인지는 확인하지 않았어요. Google AI Pro 해지와의 인과관계나 Gemini 키·과금 상태도 확인하지 않았어요. 현재 증거는 provider 이전 결정의 근거가 아니에요.

실제 티켓 샘플 업로드는 자동 승인 검토에서 두 번 거절돼 실행되지 않았어요. 두 번째 거절은 사용자의 실행 동의가 구체적인 티켓 payload와 외부 목적지를 승인한 것으로 인정되지 않았다는 사유였어요. 재차 우회하지 않고 합성 이미지 경로로 확인했어요. 외부 OCR 모델 도달 여부가 확인되지 않은 요청을 성공한 모델 호출로 세지 않아요.

상태·시간·정제된 진단은 `results.json`에 있어요. 최초 진단 시에는 앱 코드·환경 설정을 변경하지 않았어요. 아래 후속 수정에서도 환경 변수와 배포는 변경하지 않았어요. 테스트용 3714 서버는 종료하고 기존 서버는 유지했어요.


## 코드 수정과 재검증

사용자가 코드 원인 확인과 수정을 요청한 뒤 다음 사항을 확인·반영했어요.

- 같은 Upstash 호스트가 공용 DNS 1.1.1.1과 8.8.8.8에서도 ENOTFOUND를 반환했어요. 로컬 DNS에만 국한된 문제는 아니지만 주소 오타·삭제 등의 관리상 원인은 미확인이에요.
- 공통 rate limiter의 생성·통신 예외를 처리해 OCR/티켓 공유는 비용 보호를 유지한 채 unavailable로 차단하고, KOBIS는 기존 fail-open 정책에 따라 검색을 유지해요. OCR/공유 라우트는 저장소 장애를 실제 한도 초과(429)와 구분해 JSON 503을 반환해요.
- [Upstash 공식 문서](https://upstash.com/docs/redis/sdks/ratelimit-ts/features#timeout)와 설치 SDK에서 timeout이 success:true로 반환되는 동작을 확인했어요. reason:timeout도 같은 장애 경로로 처리해 OCR/공유가 제한 검사를 우회하지 않게 했어요.
- 현재 작업본에 빠져 있던 main의 407393e(#773) OCR 수정과 회귀 테스트를 그대로 반영했어요. 자동 모델 재시도는 0회이며, HTTP/네트워크 실패를 정상 빈 인식 결과와 구분해 실패 안내를 표시해요. 이번 503도 랜딩·드로어에서 문서 보존·버튼 처리 해제·같은 파일 재시도를 검사했어요.
- 수정한 프로덕션 빌드에서 같은 합성 JPEG POST가 **503 application/json, 4.325초**, 본문 **{"error":"Rate limit is unavailable"}**로 반환됐어요. 원본 URL/토큰 없이 scope와 장애 메시지만 서버 로그에 남아요.
- 생성 오류·통신 오류·SDK timeout을 주입한 테스트에서 실제 OCR/공유 핸들러가 외부 호출 없이 503을 반환했어요. 관련 테스트 32개, 전체 1,313개(142파일)가 통과했고 typecheck, lint, build, git diff --check도 통과했어요.
- Vercel 배포 로그를 읽으려 했지만 CLI 인증 토큰이 유효하지 않아 조회하지 못했어요. 배포의 정확한 원인은 여전히 확정하지 않아요.

**완료 범위:** 코드 오류 처리와 실패 안내 수정. **남은 외부 장애:** 유효한 Upstash 연결 설정 복구 후 OCR 200·실제 인식 검증. 오류 상태를 503으로 제어한 것이 OCR 복구 완료를 뜻하지 않아요. provider 이전 판단 근거도 아직 없어요.


## 연결 설정 출처 추가 확인

실제 로컬 실행은 .env.local의 KV_REST_API_URL을 사용하며, 실패 로그의 Upstash 호스트와 일치해요. UPSTASH_REDIS_REST_URL은 런타임에 없으므로 두 변수의 우선순위 충돌이 아니에요. .env.local의 파일 수정 시각은 2026-08-03 00:24:56(로컬 시각)이고 이번 작업에서는 수정하지 않았어요. 이 시각만으로 마지막 정상 연결 시점이나 마지막 Redis 사용 시점을 추론하지 않아요.

서비스 전체 장애와 특정 DB 주소의 소멸은 구분해야 해요. [Upstash 공식 FAQ](https://upstash.com/docs/redis/help/faq)는 무료 DB가 최소 30일 비활성 이후 경고 이메일을 거쳐 자동 보관되며, 데이터 백업 후 DB 인스턴스가 제거된다고 설명해요. 따라서 사용자가 코드를 바꾸지 않아도 연결이 끊길 수 있는 원인 후보이지만, 이 DB의 요금제·마지막 사용 시각·보관 상태를 조회하지 못했으므로 이번 원인으로 확정하지 않아요. DB 삭제·재생성 또는 기존 주소 유지 여부도 관리 콘솔 확인이 필요해요.
