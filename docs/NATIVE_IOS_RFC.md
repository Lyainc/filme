# RFC: 네이티브 iOS 전환 — 자산 실측과 경로 선택

상태: **초안 / 결정 대기.** 작성 2026-08-08. 코드 변경을 유발하지 않는 조사 문서다.

이 문서는 "네이티브로 갈까"를 설득하지 않는다. 갈 경우 **무엇이 이식되고 무엇이 버려지는지**를
실측으로 고정해, 경로 선택이 감이 아니라 숫자 위에서 이뤄지게 하는 게 목적이다. 아직 정해지지
않은 건 정해지지 않았다고 적었다.

## 2. 이미 렌더러가 둘이다

전환 논의에서 제일 먼저 알아야 할 사실. **프리뷰와 저장은 같은 코드로 안 그린다.**

- **프리뷰** = React DOM + CSS (`linear-gradient` 29곳, `mix-blend-mode` 6곳, `-webkit-line-clamp` 6곳,
  SVG 필터 `feTurbulence`/`feDiffuseLighting`/`feComponentTransfer` 등 14개 primitive)
- **저장** = canvas 픽셀 연산 (`applyCssColorFilterToPixel`, `bakeColorFilter`, `compositeOverlay`).
  iOS Safari가 `ctx.filter`를 무시해서(#490/#495) 색보정을 픽셀 단위로 직접 굽는 경로를 따로 만들었다.

둘이 어긋나는 걸 CI에서 잡으려고 픽셀 diff 회귀 테스트가 있고(#512), **그 테스트는 지금 불안정하다
(#660 열림 — 기본 5000ms 타임아웃에 간헐 실패).**

여기에 네이티브 렌더러를 더하면 드리프트가 **3-way**가 된다. 비용이 선형으로 늘지 않는 지점이라,
경로 선택에서 이게 가장 무거운 변수다. "같은 티켓이 웹 프리뷰·웹 저장·앱에서 픽셀로 같은가"를
누가 어떻게 보증할지는 경로마다 답이 달라야 한다.

## 3. 재작성이 어려운 두 곳

### feTurbulence 종이결 (#471)

물리재질 3종(artpaper·vintage·newspaper)이 SVG `feTurbulence(fractalNoise)`로 결을 만든다. 값은
계산이 아니라 **실기기 육안 튜닝**으로 잡혔다(`textureRecipes.ts:146`, #561에서 baseFrequency를
0.55→0.4로 내렸다가 0.7로 되올린 기록이 남아 있다).

- SwiftUI/Core Image에 SVG 필터 체인 등가물이 없다 → Metal 셰이더 재작성, 또는 결 타일을 미리
  래스터화해 번들(용량 ↑, intensity 연속 조절이 어려워짐)
- `react-native-svg`는 필터 지원이 부분적이고 `feTurbulence`는 플랫폼별로 갈린다

**튜닝값이 눈으로 맞춰진 것**이라 이식 후 "수식은 같은데 안 똑같아 보이는" 상태가 되기 쉽다.
새 플랫폼에서 다시 육안 튜닝이 필요하다고 보는 게 맞다.

### 색보정 픽셀 알고리즘

반대로 이건 **좋은 소식이다.** `applyCssColorFilterToPixel`은 CSS/SVG Filter Effects 스펙을 0..255
정수 픽셀에 구현한 순수 함수다. 플랫폼 의존이 없어서 Swift로 거의 1:1 포팅된다 — 캡처 파이프라인
1,031줄 중 canvas 배관이 아니라 이 알고리즘 부분은 자산으로 남는다.

## 4. 경로 후보

재작성 줄 수는 §1 표에서 산술로 뽑은 값이다. 실제 공수는 언어·프레임워크 생산성 차이가 있어
줄 수에 비례하지 않는다 — **상대 크기 비교용으로만** 읽을 것.

### A. WKWebView 래핑 (Capacitor 또는 직접)

기존 웹을 그대로 감싼다. 재작성 0줄, 네이티브 브릿지(공유·사진 저장·카메라)만 추가.

- 렌더러 드리프트 증가 없음. 무드·캡처·셸 전부 유지
- 폰트·SVG 필터 문제 전부 회피
- **App Store Guideline 4.2 (Minimum Functionality) 리젝 리스크**가 핵심 변수다. 웹을 감싸기만 한
  앱은 거절 사유가 된다. 네이티브 기능(사진 라이브러리 연동, 위젯, 공유 익스텐션, 오프라인)을
  실제로 얹어야 통과 근거가 생긴다
- 앱을 만드는 동기가 "앱스토어 노출"이면 이 경로로 충분하고, "네이티브 성능/느낌"이면 답이 아니다

### B. 하이브리드 — 셸은 네이티브, 티켓 렌더는 WebView

에디터 셸(7,174)만 SwiftUI로 쓰고, 티켓 프리뷰·저장은 WebView에 남긴다.

- 렌더러 드리프트 증가 없음(티켓 그리는 코드가 하나로 유지됨)
- 4.2 리젝 리스크 해소
- 대가: 네이티브↔WebView 상태 동기화 계층이 새로 생긴다. 편집이 실시간 프리뷰라 왕복 빈도가
  높아서, 이 다리가 성능·복잡도의 새 병목이 될 수 있다
- 재작성 ≈ 7,600줄

### C. React Native / Expo

- 도메인 utils(2,262)·훅 상태 로직 재사용, UI 전량 재작성
- CSS gradient·`-webkit-line-clamp`·`mix-blend-mode`·SVG 필터가 전부 RN 등가물로 바뀌어야 한다.
  §3의 feTurbulence가 여기서 막힌다
- 재작성 ≈ 13,000줄 + 3-way 드리프트
- TS를 계속 쓰니 도메인 코드 이중 관리는 피한다

### D. SwiftUI 전면 네이티브

- UI 전량 재작성 + 도메인 TS(2,262 + 612)도 Swift 포팅 → **같은 로직이 두 언어에 존재**하게 된다.
  웹을 계속 운영한다면 이중 관리가 영구 비용이다
- 렌더 품질·성능 상한은 가장 높다. Metal로 재질을 다시 쓰면 §3 문제가 오히려 기회가 된다
- 재작성 ≈ 16,000줄 + 3-way 드리프트

## 5. 지금 해도 되는 사전작업 / 하면 안 되는 것

이 절이 이 문서의 실용적 결론이다.

### 지금 해도 되는 것 (경로와 무관하게 이득)

1. **죽은 코드 삭제.** 전수 스캔 결과 미사용 파일은 `src/components/ui/InfoTooltip.tsx` 하나(107줄)
   였고 이 RFC와 같은 브랜치에서 지웠다. **레포는 이미 깨끗하다** — "정리해서 이식량을 줄인다"로
   벌 수 있는 게 사실상 없다는 게 측정 결과다.
2. **폰트 라이선스·포맷 확인**(조사, 코드 무변경). 지금 티켓이 쓰는 폰트는 7종이다:
   `Pretendard Variable`·`IceJaram`(로컬 woff2) + `JetBrains Mono`·`Instrument Serif`·`Nunito`·
   `Share Tech Mono`(`next/font/google`) + 시스템 폴백. **woff2는 iOS 앱에 직접 못 번들한다**(ttf/otf
   필요) 하고, Google Fonts를 앱에 번들하는 건 웹 서빙과 라이선스 조건이 다를 수 있다. 결과가
   경로 선택(특히 A/B vs C/D)에 영향을 주므로 먼저 확인할 값어치가 있다.
3. **`#660` 픽셀 diff 테스트 안정화.** 네이티브가 3번째 렌더러가 되기 전에, 2-way 드리프트를
   잡는 그물이 먼저 튼튼해야 한다. 전환과 무관하게 지금도 CI 신뢰도 문제다.

### 지금 하면 안 되는 것 (경로 미정 상태의 투기적 리팩터링)

아래는 "네이티브 대비"라는 이름으로 하기 쉬운데, **경로 A/B로 결정되면 전부 순손실**이다.
결정 전에는 손대지 않는 게 맞다.

- 영속 계층 추상화(`localStorage`/IndexedDB를 인터페이스 뒤로) — A/B에선 불필요
- 무드 레이아웃을 좌표 데이터로 뽑아내기 — A/B에선 무의미하고, C/D여도 어느 형태가 맞는지는
  타깃 프레임워크가 정해져야 안다
- API 클라이언트 계층 신설 — 네이티브는 그냥 HTTP를 부르면 된다. 지금 계층을 만들 이유가 없다
- 캡처 파이프라인 인터페이스화 — 구현이 하나뿐인 인터페이스가 된다

## 6. 경로와 무관한 리스크

1. **TMDB 저작권 (#537 열린 질문 2, 미해결).** 포스터를 앱에서 내려받아 사용자 이미지에 합성해
   공유한다. 앱스토어 심사는 웹보다 이 축에 엄격하다. TMDB 공식 로고 귀속도 아직 텍스트 문구뿐이다
   (이미지 에셋 미확보). **네이티브 착수 전에 결론이 필요한 항목이다.**
2. **rate limit이 IP 기반이다.** `checkOcrRateLimit`/`checkKobisRateLimit`/`checkTmdbRateLimit`이 모두
   클라이언트 IP를 키로 쓴다(`ratelimit.ts:90`). 앱 사용자는 웹보다 셀룰러 비중이 높고 캐리어 NAT
   뒤에서 IP를 공유해서, **정상 사용자가 남의 트래픽으로 429를 맞는 빈도가 웹보다 올라간다.**
   기기 단위 식별자로 옮길지가 네이티브 전환과 함께 결정돼야 한다.
3. **비용 포스처.** 공유 파이프라인은 Hobby 한도를 넘지 않으려고 의도적으로 조여둔 상태다(#194 —
   자동 발급 폐기, TTL 3일). 앱 사용자당 호출 패턴이 웹과 다르면 이 가정이 다시 계산돼야 한다.
4. **오프라인.** 지금은 OCR·KOBIS·TMDB가 전부 서버 왕복이다. 앱에서 "비행기 모드에서도 티켓을
   만든다"를 기대한다면, 렌더는 로컬이어도 검색·OCR은 못 쓴다는 걸 UX가 받아들여야 한다.

## 7. 결정이 필요한 것

이 RFC는 답을 고르지 않는다. 아래 셋이 정해지면 §5의 "하면 안 되는 것" 목록이 실행 목록으로 바뀐다.

1. **앱을 만드는 동기는 무엇인가** — 앱스토어 유통 채널이 목적이면 A/B, 네이티브 렌더 품질과
   조작감이 목적이면 C/D다. 이게 나머지 둘을 대부분 결정한다.
2. **웹을 계속 운영하는가** — 계속 운영하면 D의 로직 이중 관리가 영구 비용이 되고, 웹을 접는
   전환이면 그 비용이 사라진다.
3. **티켓 렌더가 웹과 픽셀로 같아야 하는가** — "같아야 한다"면 3-way 드리프트를 감당할 수단
   (렌더러 하나 유지 = A/B, 또는 픽셀 diff 하네스 확장)이 경로 조건이 된다.
